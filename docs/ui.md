# UI Decisions

Lasting decisions about the egui app: persistence, the clipboard watcher, save reloading, and the build stamp.

> The sections below were moved verbatim out of `CLAUDE.md` on 2026-09-18 (idea #4770), which now keeps only a pointer to each. This doc is the record: add new detail here, not to `CLAUDE.md`.

## Decisions

- **Persist inputs, never derived state**: `result`/`generated`/`pending_grid` come from a solve, and restoring them beside restored inputs they no longer match is a lie on screen. Restore is lenient by construction (`#[serde(default)]` at container level, unknown fields ignored, `Default` routed through `ChainPanel::new()`) so adding a field later cannot wipe a saved setup
- **The clipboard watcher is gated on what the viewport shows, never on where a string came from**: `FactorioApp::displayed` holds the blueprint string currently on screen whatever loaded it, and a candidate equal to it is declined. That one rule covers both re-copying something already loaded and the self-copy loop — "Copy blueprint" hands the watcher the generated block's own string while the viewport is showing that block. A guard written against the copy button specifically would need re-adding at every future call site that writes to the clipboard
- **A clipboard load never writes `blueprint_input`**: showing the user what arrived would also overwrite a string they were part-way through typing, and a background poller must not be able to destroy typing. Both load paths go through `load_string`, differing only in the `LoadSource` they report
- **`arboard` needs its non-default `wayland-data-control` feature**: plain Wayland hands the clipboard only to the *focused* surface, so without it the watcher reads nothing while the game has focus — which is the entire use case. egui-winit already pulls arboard in without it; the ui crate re-declares it to switch the feature on for the shared copy
- **Clipboard reads happen off the UI thread**: both arboard backends round-trip to another process, and a stall there is a dropped frame. The thread offers candidates over a channel and calls `request_repaint`, so an idle app still notices; `poll` returns the *newest* of a backlog, since replaying them would flash each blueprint through the viewport on the way to the one the user actually copied
- **A save is re-read when it changes on disk, but adopted silently only when that discards nothing.** Factorio autosaves every few minutes, so an availability set decoded once at import goes quietly stale for the rest of a session. `SavePickerState::poll` runs every frame — one `stat` on an unchanged file — and compares the panel's current set against the one the last import produced: equal means the reload is invisible and is taken, unequal means the tick list holds corrections and the user gets a "Save changed on disk" Reload button instead. The tick list exists to *correct* an import, so silently overwriting a correction every few minutes is the one way this feature could destroy user input. The automatic path deliberately never touches `availability_mode` either — only an explicit import may re-gate the panel, or a user who switched back to `Everything` would find the gate reapplied by an autosave
- **The reload records the signature of the last *attempt*, not of the last success.** A save caught mid-write fails to decode, and keyed on success it would be re-read on every frame — tens of megabytes per frame. Keyed on the attempt, a failing file is read once per distinct `(mtime, len)`. Both halves of that signature are load-bearing: mtime granularity is a filesystem property, and a save rewritten at the same size is routine. A failed reload leaves `status` alone (its count still describes the set actually in use) and raises `changed_on_disk` instead, so the staleness is on screen rather than silent
- **The build stamp is compared, not just displayed**: `launch.sh` launches the previous binary when a build fails, and a bare sha only answers "am I current?" for someone who already knows what HEAD is — nobody compares shas by eye. So `build.rs` stamps the commit and `build_info::check_in` asks the checkout the binary lives in how far it has moved, in a background thread, once. The three answers stay distinct: `Current`, `Stale`, and `Unknown` (no stamp, no git, or a binary copied out of its tree) — folding `Unknown` into `Current` would make every non-git build claim to be up to date
- **`build.rs` watches the git files it read, and only those that exist**: cargo caches a build script's output and, once *any* `rerun-if-changed` is emitted, reruns it only for the named paths — so without them the stamp is baked once and then lies. The paths come from `git rev-parse --git-path`, never from assembling `.git/...` by hand: this repo is developed from linked worktrees, where HEAD lives under `.git/worktrees/<name>/` while refs stay in the common dir. A path that does not exist (`packed-refs`, commonly) is dropped rather than emitted, because cargo reads a missing target as "changed" and would relink the binary on every build
- **Every `git` subprocess strips `GIT_DIR` and its eight siblings, because `current_dir` does not outrank them.** Git *exports* those variables to the hooks it runs and the commit gate builds and tests from `pre-commit`, so anything shelling out to git under the gate is silently pointed at the repository being committed to, whatever directory it was aimed at. Measured, not theorised: a test that built a throwaway repository in a tempdir and committed into it put a real commit on the real branch instead, and the stale-build check answered `Current` for a directory that was not a repository at all. Both `build.rs` and `build_info.rs` carry the strip list — a build script shares no code with its crate — and `build_info_tests` asserts on the `Command`'s own env rather than by setting variables in the test process, which is process-wide and shared with every other test thread
