# Phase 9 — Recipe Availability Gate

> Manual editing of the unlocked-recipe set, the technology graph that explains
> a refusal, and panel persistence. Composes with Phase 8's save import rather
> than replacing it: both fill the same set.

**Design:** `.claude/plans/2026-08-13-recipe-availability-gate-design.md`
**Plan:** `.claude/plans/2026-08-13-recipe-availability-gate-plan.md`

Closes the consuming half of idea #3356 (already closed by Phase 8), plus
#3380 (panel state persistence) and #3385 (availability-aware recipe picker).

## The problem

`chain::select` considered every recipe in the registry. On a Space Age dump a
mid-game player asking for chemical science hit four `AmbiguousRecipe` errors in
a row — `iron-plate`, `copper-cable`, `iron-gear-wheel`, `pipe` — each because a
`casting-*` recipe exists beside the assembler one. All four are behind a single
technology, `foundry`, deep in Vulcanus. The player was being asked to arbitrate
between a recipe they use daily and one they cannot build.

Machine selection had the same hole and it mattered more: `MachinePolicy::
fastest()` picked the fastest prototype covering a category with no regard for
buildability, so a chemical-science plan assigned three of its steps to
**electromagnetic plants** (Fulgora). The blueprint was unpasteable for most of
a playthrough.

Phase 8 fixed both *given a save file to read*. This phase makes the same gate
usable without one, and makes the refusal say what to research.

## What was built

- **`solver::tech`** — a `Technology` schema (`prerequisites`, `unlocks`) and
  registry over all 275 technologies, generated by `dump-ingest` from the same
  2.0.77 dump as the other two data files, plus a reverse index so
  `unlockers_for(recipe)` answers "which research grants this" without scanning.
  Ingested for *explanation only*: nothing selects on it.
- **`solver::availability`** — the `Availability` model, reconciled with
  Phase 8's (see "The merge" below). `all_available_recipe_names()` is the seed
  the UI hands out.
- **Gated selection** — `available_candidates_for` beside the unchanged
  `candidates_for`, `RecipeLocked`/`MachineLocked` naming the technology.
- **The chain panel's "Available recipes" section** — a mode radio, a search
  box, tick/untick-all-matching, a scrolling checkbox list and a count line.
- **`ui::persist`** — the panel's inputs survive a restart, via eframe's
  non-default `persistence` feature.

## Decisions worth carrying forward

Recorded in `CLAUDE.md` under "Decisions from previous phases". The ones this
phase turned on:

- **The set is recipe names, never technologies.** A save exposes per-recipe
  unlocked flags; researched technologies are not readable. So every source —
  a hand edit, a save import, a future projection — produces the same thing, and
  the technology graph is left to do the one job it can: explaining.
- **"No recipe" and "no recipe you can build" stay distinguishable.** `solve`'s
  raw-resource test keeps calling the *ungated* `candidates_for`. Gated in
  place, a locked intermediate two levels down would report as a bus
  requirement — a plan telling the player to belt 45/s of a Vulcanus casting
  product, looking entirely successful. Both sessions arrived at this
  independently, by different routes.
- **`enabled: true` is allowed under every variant.** Without it, unticking one
  recipe would silently lock the 323 the game grants at the start.
- **Editing is subtractive.** Entering the mode seeds the set from what is
  already available, so the switch alone changes no result.
- **Persist inputs, never derived state.** A restored plan beside restored
  inputs it no longer matches is a lie on screen.

## The merge

Phase 8 (save-derived availability, another session) and this phase were
designed the same day against the same problem and landed within hours of each
other. This branch merged onto it rather than either replacing the other — the
design had named the contract between them up front ("exactly one thing: a set
of unlocked recipe names"), which is what made the merge a reconciliation rather
than a rewrite. See the merge commit for the full reasoning; in short:

- One `Availability`, in `solver::availability`, re-exported as
  `chain::Availability`. This phase's variant names and `BTreeSet`.
- One error pair, `RecipeLocked`/`MachineLocked` (Phase 8's names) carrying
  `unlocked_by` (this phase's explanation).
- One availability set in the UI: a decoded save writes into the panel's
  `available_recipes` and flips the mode, so an import is a starting point the
  tick list can then correct rather than a second, competing constraint.

Three of Phase 8's assertions encoded rules the reconciliation deliberately
changes; each was rewritten rather than worked around, and the reasoning lives
in the tests. The merge also fixed a bug this branch had shipped: `solve`'s
locked-item checks ran before `select_recipe` saw `recipe_overrides`, so an
override that rescued a locked recipe when called directly failed inside a
plan. Phase 8's suite had a test for that property; this branch's did not.

## Corrections to the design doc

Two claims in the design proved wrong against the real data, and are wrong in
the doc as written:

- **"The never-unlockable eight are candidates today, so excluding them is a
  live bug fix."** They are not candidates: all eight are also `hidden: true`,
  so `candidates_for`'s long-standing hidden filter had already dropped them.
  The exclusion is still right, but what it protects is the UI's seeded
  tick-list, not chain selection.
- **The plan's `iron-ore` fixture for "a genuinely raw item".** `iron-ore` is
  produced by the Space Age asteroid-crushing recipes, so it is not raw. `wood`
  is, and is what the test uses.

## Status

Every crate's suite passes. What no test covers is the same thing Phase 8 left
open and one more:

- **Pasting a generated block into Factorio.** Unchanged from Phase 7.
- **Driving the availability UI by hand.** The headless egui harness exercises
  the real render path and the reported case end to end
  (`availability_tests.rs::the_reported_case_solves_with_no_overrides`), but
  nobody has clicked the tick list in a running window.
- **Persistence across a real restart.** Tested at the serde layer; eframe's
  own storage round-trip needs an app lifecycle.
